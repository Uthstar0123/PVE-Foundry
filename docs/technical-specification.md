# Техническое задание: платформа управления инфраструктурой Proxmox

- **Рабочее название:** Proxmox Orchestrator
- **Версия документа:** 2.0
- **Статус:** Утверждено владельцем 18.11.2026
- **Тип системы:** Self-hosted Web Application / Infrastructure Orchestrator
- **Целевая платформа:** Proxmox VE 9.2.10 (`pve-manager/9.2.10/43df2e01f27a1a19`)
- **Условие начала реализации:** только после явного утверждения данного документа и плана выполнения владельцем

---

## 1. Общее описание

Разрабатываемая система представляет собой локальную веб-платформу для централизованного развёртывания, настройки и масштабирования виртуальных машин, LXC-контейнеров и контейнеризированных приложений в инфраструктуре Proxmox VE.

Платформа не заменяет стандартный интерфейс Proxmox. Она предоставляет надстройку для повторяемых сценариев:

- создание ВМ и LXC по шаблонам;
- установка приложений из каталога;
- развёртывание инфраструктуры из Terraform/OpenTofu-конфигураций;
- настройка гостевых систем;
- управление Docker и Docker Compose внутри ВМ;
- выполнение операций в фоновом режиме с логами и аудитом;
- вертикальное масштабирование ресурсов;
- резервное копирование конфигурации и состояния платформы.

Система предназначена для рабочей инфраструктуры. Первоначально ею пользуется один администратор, но требования к безопасности, восстановлению и аудиту сохраняются.

## 2. Исходные условия и ограничения

1. Основная целевая среда — Proxmox VE 9.2.10.
2. Необходимо поддерживать ВМ и LXC.
3. Docker поддерживается внутри гостевых систем; в MVP Docker запускается в выделенных ВМ.
4. Первоначально существует один пользователь с ролью администратора.
5. Веб-интерфейс не публикуется в Интернете и доступен только из локальной сети.
6. Proxmox-хост использует статический IP-адрес.
7. Создаваемые ВМ и LXC преимущественно получают сетевые настройки через DHCP.
8. Каталоги и IaC-конфигурации могут загружаться из произвольных Git-репозиториев и архивов.
9. Произвольный внешний код считается недоверенным, независимо от того, кто его загрузил.
10. Панель и база данных размещаются в отдельной управляющей ВМ.
11. Выполнение внешнего IaC и установочного кода производится в отдельном изолированном runner-окружении.
12. Docker не устанавливается на Proxmox-хост ради работы панели.

## 3. Цели проекта

### 3.1. Основные цели

1. Сократить количество ручных операций по созданию и настройке инфраструктуры.
2. Предоставить единый локальный веб-интерфейс для управления ресурсами и приложениями.
3. Обеспечить повторяемость развёртываний через Infrastructure as Code.
4. Показывать план изменений до их применения.
5. Сохранять историю операций, ошибок и конфигураций.
6. Ограничить последствия ошибок и вредоносного кода из внешних источников.
7. Обеспечить восстановление платформы после сбоя управляющей ВМ.

### 3.2. Нефункциональная цель

Система должна оставаться удобной для одного администратора без избыточной enterprise-инфраструктуры: Kubernetes, Kafka, RabbitMQ и распределённые базы данных в MVP не используются.

## 4. За пределами первой версии

В MVP не входят:

- публичный доступ к панели;
- мультитенантность и биллинг;
- несколько одновременно активных администраторов;
- OIDC, LDAP и сложная RBAC;
- автоматическое горизонтальное масштабирование по нагрузке;
- Kubernetes;
- HA-кластер самой платформы;
- веб-консоль Proxmox и интерактивный веб-терминал;
- автоматический запуск непроверенных shell-скриптов на Proxmox-хосте;
- поддержка произвольных облачных провайдеров;
- гарантированная совместимость с любой Terraform-конфигурацией;
- автоматический откат через удаление частично созданной инфраструктуры;
- управление Docker внутри LXC.

Перечисленные функции могут быть добавлены после стабилизации основного контура.

## 5. Пользователи и роли

### 5.1. MVP

Предусмотрен один пользователь:

- **Administrator** — полный доступ к настройкам, источникам, ресурсам, задачам, секретам и восстановлению.

### 5.2. Архитектурный резерв

Модель данных не должна жёстко предполагать наличие только одного пользователя. В последующих версиях предусматриваются роли:

- **Operator** — управление ресурсами и приложениями без изменения глобальных настроек;
- **Viewer** — просмотр состояния, метрик и логов;
- **Auditor** — просмотр истории без управления ресурсами.

## 6. Архитектура

### 6.1. Логические компоненты

```text
┌────────────────────────────────────────────────────────────┐
│                       Browser / LAN                        │
└────────────────────────────┬───────────────────────────────┘
                             │ HTTPS
┌────────────────────────────▼───────────────────────────────┐
│                   Management VM                            │
│                                                            │
│  React SPA → Go API → PostgreSQL                           │
│                  │        └─ Audit / Jobs / Metadata       │
│                  ├─ Artifact storage                        │
│                  ├─ Read-only Proxmox inventory             │
│                  └─ Job dispatcher                          │
└────────────────────────────┬───────────────────────────────┘
                             │ authenticated job channel
┌────────────────────────────▼───────────────────────────────┐
│                     Isolated Runner VM                     │
│                                                            │
│  Runner service                                            │
│    ├─ OpenTofu / Terraform HCL                             │
│    ├─ Ansible                                              │
│    ├─ Artifact verification                                │
│    ├─ Resource limits and timeouts                         │
│    └─ Log streaming                                        │
└──────────────┬──────────────────────┬──────────────────────┘
               │                      │
        Proxmox write API       SSH to guests
               │                      │
       ┌───────▼────────┐      ┌──────▼──────────────────┐
       │  Proxmox VE    │      │      Guest VMs / LXC    │
       │  VM / LXC      │      │ Applications / Docker   │
       └────────────────┘      └─────────────────────────┘
```

### 6.2. Management VM

Отвечает за:

- веб-интерфейс и REST API;
- аутентификацию и сессии;
- хранение метаданных;
- чтение инвентаря Proxmox;
- постановку задач в очередь;
- хранение загруженных пакетов;
- приём и отображение логов;
- аудит;
- резервное копирование.

Management VM не выполняет произвольный внешний код.

### 6.3. Runner VM

Отвечает за:

- `init`, `validate` и `plan` OpenTofu;
- `apply` после подтверждения;
- выполнение Ansible;
- проверку пакетов и зависимостей;
- ограничение ресурсов и времени выполнения;
- потоковую передачу логов;
- возврат результата и фактического состояния.

В MVP используется один runner. Возможность запуска нескольких runners закладывается в протокол, но не реализуется как обязательная функция.

### 6.4. Взаимодействие с Proxmox

Используются разные токены:

- **read-only token** для инвентаря Management VM;
- **write token** для Runner VM с минимально необходимыми правами.

Права ограничиваются выделенными Proxmox pools, storage, сетями и другими необходимыми объектами. Root-пароль Proxmox в платформе не сохраняется.

Runner не получает постоянный SSH-доступ к Proxmox-хосту. Если отдельная операция provider требует SSH, она выносится в явно документированное исключение и не включается автоматически.

## 7. Функциональные требования

### 7.1. Первоначальная настройка

Мастер настройки должен:

1. Создать первого администратора без пароля по умолчанию.
2. Настроить адрес Proxmox API и проверить TLS.
3. Принять и проверить API Token.
4. Проверить доступные ноды, storage, bridge и pools.
5. Настроить параметры runner.
6. Проверить наличие VM и LXC templates.
7. Задать локальный адрес панели и параметры HTTPS.
8. Выполнить тестовое read-only подключение.

До завершения настройки операции изменения инфраструктуры должны быть недоступны.

### 7.2. Аутентификация и безопасность панели

Обязательные функции:

- вход по имени пользователя и паролю;
- Argon2id для хэширования паролей;
- безопасные HTTP-only, Secure и SameSite cookie;
- защита от CSRF;
- ограничение частоты попыток входа;
- завершение активных сессий;
- HTTPS в локальной сети через доверенный внутренний или самоподписанный сертификат;
- аудит входов и изменений настроек.

2FA/TOTP рекомендуется заложить в модель, но может быть реализовано после MVP.

### 7.3. Инвентарь Proxmox

Панель должна отображать:

- ноды и их состояние;
- ВМ и LXC;
- VMID, имя, тип, ноду, pool и теги;
- CPU, RAM и диски;
- сетевые интерфейсы и обнаруженные IP-адреса;
- storage и доступное пространство;
- состояние запуска;
- связь ресурса с deployment платформы.

Должна выполняться периодическая синхронизация с фактическим состоянием Proxmox. Ресурсы, созданные вне платформы, отображаются как внешние и не изменяются без явного импорта.

### 7.4. Управление ВМ и LXC

Поддерживаемые операции:

- создание ВМ клонированием Cloud-Init Template;
- создание LXC из подготовленного шаблона;
- запуск, остановка и перезапуск;
- изменение количества CPU и RAM;
- увеличение диска;
- изменение сетевых параметров в пределах поддерживаемой модели;
- удаление после отдельного подтверждения;
- просмотр истории изменений.

Требования:

- длительные операции выполняются асинхронно;
- повтор HTTP-запроса не должен создавать дубликаты;
- одновременные конфликтующие операции над одним ресурсом блокируются;
- уменьшение диска не выполняется;
- операции, требующие перезапуска, заранее обозначаются в UI;
- удаление требует ввода имени ресурса;
- удаление внешних ресурсов через платформу запрещено до их явного импорта.

### 7.5. DHCP и сетевая конфигурация

В MVP:

- пользователь выбирает bridge и при необходимости VLAN;
- по умолчанию используется DHCP;
- панель обнаруживает и отображает назначенные адреса;
- для ВМ предпочтительно использовать QEMU Guest Agent;
- Ansible подключается к обнаруженному адресу;
- смена DHCP-адреса не должна приводить к потере ресурса из инвентаря.

Дополнительно пользователь может указать статический IP, если это поддерживает выбранный шаблон.

В последующих версиях могут быть добавлены DHCP reservations, локальный DNS и NetBox.

### 7.6. Каталог приложений

Каталог должен поддерживать:

- встроенные пакеты;
- Git-репозитории;
- загруженные `.zip` и `.tar.gz` архивы;
- несколько версий одного приложения;
- параметры установки;
- описание требуемых ресурсов;
- health checks;
- обновление и удаление приложения.

Каждый пакет содержит:

```text
application-package/
├── manifest.yaml
├── inputs.schema.json
├── infrastructure/
├── configuration/
├── checks/
└── documentation/
```

Манифест должен описывать:

- уникальный ID и версию;
- название и описание;
- поддерживаемый тип развёртывания;
- требования к CPU, RAM и диску;
- параметры сети;
- используемые providers и модули;
- секреты, которые потребуются;
- поддерживаемые операции обновления и удаления;
- возможность вертикального и горизонтального масштабирования;
- health check;
- ограничения и лицензии.

### 7.7. Добавление внешнего источника

При добавлении источника система должна:

1. Загрузить содержимое.
2. Зафиксировать commit SHA или хэш архива.
3. Проверить структуру и размеры файлов.
4. Запретить path traversal, опасные symlink и выход за рабочий каталог.
5. Проверить манифест и JSON Schema.
6. Показать требуемые providers и операции.
7. Запустить проверку только в runner.
8. Показать план изменений.
9. Получить явное подтверждение администратора.
10. Выполнить установку как отдельную отслеживаемую задачу.

Автоматическое обновление внешних источников и автоматический apply запрещены в MVP.

### 7.8. Terraform/OpenTofu

Поддерживаются:

- загрузка архива;
- подключение Git-репозитория;
- выбор каталога конфигурации;
- переменные и секреты;
- `fmt`, `validate`, `plan`, `apply`;
- отображение plan;
- отдельный state на deployment;
- блокировка state;
- история ревизий;
- повторный plan для обнаружения drift.

Ограничения:

- источник может быть любым, но набор исполняемых providers ограничивается политикой платформы;
- произвольные `local-exec`, внешние data sources и неизвестные providers считаются опасными;
- поддержка конкретной конфигурации подтверждается проверкой в runner;
- секреты не выводятся в открытых логах;
- state не сохраняется в Git;
- state и резервные копии защищаются и шифруются;
- `destroy` является отдельной операцией с дополнительным подтверждением.

### 7.9. Настройка гостевых систем

Для ВМ:

- Cloud-Init задаёт пользователя, SSH-ключи, сеть и базовые параметры;
- QEMU Guest Agent помогает определить готовность и сетевые адреса;
- Ansible устанавливает и настраивает приложения.

Для LXC:

- используется подготовленный шаблон;
- начальная конфигурация выполняется поддерживаемыми средствами Proxmox;
- дальнейшая настройка выполняется через Ansible по SSH.

Ansible не должен использоваться для постоянного хранения незашифрованных секретов в репозитории или логах.

### 7.10. Очередь задач и логи

Каждая операция представляется задачей со статусами:

```text
QUEUED → RUNNING → SUCCEEDED
                 → FAILED
                 → CANCELLED
```

Дополнительно допускается состояние `WAITING_APPROVAL`.

Система должна хранить:

- инициатора;
- тип операции;
- целевой ресурс;
- время создания, начала и завершения;
- шаги выполнения;
- логи;
- код ошибки;
- источник и ревизию конфигурации;
- хэш плана и подтверждение apply.

Требования:

- логи отображаются в реальном времени;
- секреты маскируются;
- логи можно скачать;
- задачи не теряются при перезапуске панели;
- после сбоя выполняется сверка состояния;
- незавершённая задача не повторяется слепо, если результат неизвестен;
- отмена не должна представляться как гарантированный откат.

### 7.11. Docker и Docker Compose

После базового MVP добавляются:

- регистрация Docker endpoint в выделенной ВМ;
- подключение по TLS;
- список контейнеров и Compose-проектов;
- запуск, остановка и перезапуск;
- просмотр логов;
- развёртывание Compose;
- обновление образа и пересоздание;
- основные метрики CPU и RAM.

Незащищённый Docker TCP API не используется. Docker Socket Management VM или Runner VM не передаётся внешнему коду.

### 7.12. Масштабирование

В MVP реализуется вертикальное масштабирование:

- изменение vCPU;
- изменение RAM;
- увеличение диска.

Горизонтальное масштабирование реализуется позже и только для приложений, чей манифест явно описывает:

- допустимое количество экземпляров;
- общие данные и внешние зависимости;
- балансировку;
- health checks;
- порядок добавления и удаления экземпляров.

### 7.13. Caddy и локальные домены

Функция не входит в первый работоспособный MVP и добавляется после стабилизации Docker:

- локальные доменные имена;
- проксирование на обнаруженный адрес приложения;
- HTTPS внутренним CA или доверенным сертификатом;
- WebSocket proxy;
- проверка доступности после добавления маршрута.

Публичный Let's Encrypt не является обязательным, поскольку панель и приложения первоначально работают в локальной сети.

### 7.14. Резервное копирование и восстановление

Резервная копия должна включать:

- PostgreSQL;
- конфигурацию платформы;
- загруженные пакеты и их метаданные;
- OpenTofu state или сведения для доступа к защищённому state backend;
- ключи шифрования по отдельной защищённой процедуре;
- аудит и историю задач.

Требования:

- автоматическое расписание;
- хранение копии вне Management VM;
- проверка целостности;
- документированная процедура восстановления;
- тестовое восстановление перед признанием релиза готовым;
- синхронизация с Proxmox после восстановления.

Backup Proxmox-гостей выполняется штатными средствами Proxmox/PBS и не подменяется копией базы платформы.

## 8. Модель данных

Основные сущности:

- `users` — пользователи;
- `sessions` — активные сессии;
- `clusters` — подключённые Proxmox-кластеры;
- `nodes` — ноды;
- `resources` — ВМ и LXC;
- `deployments` — логические развёртывания;
- `deployment_revisions` — версии конфигурации;
- `catalog_sources` — источники каталога;
- `catalog_items` — приложения и версии;
- `artifacts` — архивы, манифесты и plan-файлы;
- `jobs` — задачи;
- `job_steps` — шаги;
- `job_events` — потоковые события и логи;
- `secrets` — ссылки на зашифрованные секреты;
- `docker_endpoints` — подключения к Docker в гостях;
- `audit_events` — аудит;
- `settings` — настройки платформы.

Секреты не хранятся открытым текстом в обычных полях БД. Ключ шифрования не должен находиться только в той же резервной копии, что и зашифрованные данные.

## 9. Основной API

### 9.1. Настройка и авторизация

- `POST /api/v1/setup`
- `POST /api/v1/auth/login`
- `POST /api/v1/auth/logout`
- `GET /api/v1/auth/session`

### 9.2. Инфраструктура

- `GET /api/v1/clusters`
- `GET /api/v1/nodes`
- `GET /api/v1/resources`
- `GET /api/v1/resources/:id`

## 10. Нефункциональные требования

### 10.1. Надёжность

- Сбой панели не должен останавливать ВМ, LXC и приложения.
- После перезапуска состояние синхронизируется с Proxmox.
- Все длительные операции сохраняются в БД.
- Операции имеют таймауты и диагностируемые ошибки.
- Неизвестный результат операции не должен автоматически приводить к повторному созданию ресурсов.

### 10.2. Производительность

- Обычные запросы к локальным данным: целевое p95 до 300 мс при штатной нагрузке.
- Изменяющие операции возвращают задачу и не удерживают HTTP-запрос до завершения.
- Инвентарь не должен перегружать Proxmox API частыми опросами.
- Логи передаются с ограничением размера буфера и без неограниченного потребления памяти.

### 10.3. Безопасность

- Management VM не запускает внешний код.
- Runner не имеет root SSH к Proxmox-хосту.
- Секреты шифруются и маскируются.
- Действия `apply`, `destroy` и удаление ресурсов подтверждаются отдельно.
- Внешние источники фиксируются по неизменяемой ревизии.
- Размеры архивов, глубина путей, время и ресурсы задач ограничиваются.
- Панель остаётся доступной только из разрешённых локальных сетей.

### 10.4. Совместимость

Первоначально гарантируется только:

- Proxmox VE 9.2.10;
- Linux AMD64 для Management VM и Runner VM;
- поддерживаемые Debian/Ubuntu VM templates;
- выбранные и зафиксированные версии OpenTofu и `bpg/proxmox`;
- актуальные Chrome, Firefox и Edge.

Поддержка других версий добавляется после отдельного тестирования.

### 10.5. Сопровождаемость

- миграции БД версионируются;
- зависимости фиксируются;
- конфигурация отделяется от кода;
- API версионируется;
- логи структурируются;
- критические компоненты покрываются автоматическими тестами;
- установка и восстановление документируются.

## 12. Критерии приёмки MVP

MVP считается готовым, когда на тестовой инфраструктуре успешно выполнены следующие сценарии:

1. Платформа устанавливается в новую Management VM.
2. Создаётся администратор без пароля по умолчанию.
3. Подключается Proxmox 9.2.10 через ограниченный token.
4. Панель отображает ноды, ВМ, LXC и storage.
5. Создаётся ВМ из Cloud-Init Template с DHCP.
6. Создаётся LXC из шаблона с DHCP.
7. Выполняются запуск, остановка, перезапуск и изменение ресурсов.
8. Пользователь видит асинхронную задачу и её логи.
9. Из Git добавляется проверенный пакет приложения.
10. До apply отображается план, после подтверждения выполняется установка.
11. Внешний код выполняется только в Runner VM.
12. Устанавливается как минимум одно приложение в ВМ и одно в LXC.
13. Сбой и перезапуск панели не останавливают гостей и не теряют историю.
14. Повтор запроса не создаёт дубликат ресурса.
15. Удаление требует отдельного подтверждения.
16. Резервная копия создаётся и успешно восстанавливается на чистой тестовой Management VM.
17. После восстановления выполняется синхронизация с фактической инфраструктурой.
18. Все критические действия присутствуют в аудите.
