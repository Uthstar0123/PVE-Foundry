# План выполнения: PVE Foundry

- **Версия:** 1.0
- **Статус:** Утверждён владельцем 18.11.2026; этапы 0–2 завершены, программный контур этапа 3 реализован и ожидает проверки на реальном PVE
- **Связанный документ:** `docs/technical-specification.md`
- **Условие старта:** явное утверждение владельца

---

## 1. Принципы выполнения

1. До утверждения не создаются приложение, инфраструктурные модули и установочные скрипты.
2. После утверждения работа выполняется последовательно по этапам настоящего плана.
3. Сначала реализуются безопасность, задачи и восстановление, затем расширенные функции.
4. Каждый этап заканчивается тестированием и коротким отчётом.
5. Операции с рабочим Proxmox выполняются только в выделенном тестовом pool.
6. Удаление и другие необратимые операции сначала проверяются на тестовых ресурсах.
7. Секреты и реальные токены не помещаются в Git.
8. Существенное отклонение от утверждённой архитектуры требует отдельного согласования.

## 2. Последовательность этапов

```text
Этап 0: Подготовка и проверка совместимости
   ↓
Этап 1: Каркас проекта
   ↓
Этап 2: БД, настройка и авторизация
   ↓
Этап 3: Read-only интеграция с Proxmox
   ↓
Этап 4: Очередь, задачи, логи и аудит
   ↓
Этап 5: Runner и безопасный OpenTofu
   ↓
Этап 6: Жизненный цикл ВМ и LXC
   ↓
Этап 7: Каталог и установка приложений
   ↓
Этап 8: Backup, restore и приёмка базового MVP
   ↓
Этап 9: Docker и Compose
   ↓
Этап 10: Упаковка, UX и стабилизация
```

Этапы 0–8 образуют базовый MVP. Этапы 9–10 расширяют его до полного первого релиза.

## Этап 0. Подготовка и проверка совместимости

### Задачи

1. Создать отдельный тестовый Proxmox pool.
2. Создать отдельных пользователей и API Tokens:
   - read-only для Management VM;
   - ограниченный write для Runner VM.
3. Выделить тестовые storage, bridge и VLAN при необходимости.
4. Подготовить Cloud-Init VM Template с QEMU Guest Agent.
5. Подготовить LXC Template с SSH.
6. Проверить DHCP и обнаружение адресов гостей.
7. Подготовить Management VM и Runner VM.
8. Зафиксировать версии OpenTofu и `bpg/proxmox`.
9. Вручную проверить минимальные операции через provider:
   - чтение нод;
   - клонирование ВМ;
   - создание LXC;
   - изменение CPU/RAM;
   - удаление только тестовых ресурсов.
10. Задокументировать операции, которым действительно требуется SSH, и исключить их из MVP либо согласовать отдельно.

### Результат

- тестовый контур;
- проверенные templates;
- ограниченные токены;
- отчёт о совместимости с PVE 9.2.10;
- список подтверждённых возможностей provider.

### Критерий завершения

Из изолированного Runner VM успешно создаются и удаляются тестовые ВМ и LXC без root SSH к Proxmox-хосту.

### Блокирующие проблемы

Если выбранный provider не поддерживает необходимые операции на PVE 9.2.10, реализация останавливается и владельцу предлагаются варианты: другая совместимая версия provider, ограничение функций или отдельный Proxmox API adapter.

## Этап 1. Каркас проекта

### Задачи

1. Инициализировать Git-репозиторий и правила игнорирования секретов.
2. Создать структуру backend, runner и frontend.
3. Настроить Go module и TypeScript/Vite-проект.
4. Добавить конфигурацию через переменные окружения и файл настроек.
5. Настроить миграции PostgreSQL.
6. Настроить форматирование, lint и базовые тесты.
7. Настроить воспроизводимую сборку.
8. Подготовить окружение локальной разработки без подключения к рабочим ресурсам.

### Предполагаемая структура

```text
cmd/server/             # Management API
cmd/runner/             # Runner service
internal/               # Backend modules
web/                    # React SPA
migrations/             # PostgreSQL migrations
deploy/                 # Installation manifests
catalog/                # Verified built-in packages
tests/                  # Integration and E2E tests
docs/                   # Documentation
```

### Результат

Собираемый каркас Management API, Runner и React UI с автоматическими проверками.

### Критерий завершения

Чистая установка зависимостей и сборка проекта выполняются по документированным командам; базовые тесты проходят.

## Этап 3. Read-only интеграция с Proxmox

### Задачи

1. Реализовать Proxmox API client.
2. Добавить проверку TLS и диагностику ошибок соединения.
3. Реализовать чтение:
   - нод;
   - ВМ;
   - LXC;
   - storage;
   - pools;
   - сетевых интерфейсов.
4. Добавить периодическую синхронизацию и кэширование.
5. Сохранить связь внутреннего ресурса с Proxmox ID.
6. Реализовать страницы:
   - обзор;
   - ноды;
   - ресурсы;
   - хранилища;
   - карточка ресурса.
7. Отображать внешние ресурсы без возможности случайного изменения.

### Текущий результат 19.11.2026

- Реализованы API client, строгий HTTPS, custom CA, диагностика 401/403 и только GET-запросы.
- Реализованы чтение версии, нод, QEMU/LXC, storage, pools и сетевых интерфейсов.
- Добавлены 30-секундный in-memory cache, объединение параллельных запросов и фоновое обновление раз в минуту.
- Реализованы защищённый API endpoint, обзор, ноды, ресурсы, раскрываемая карточка ресурса, хранилища, pools и сеть.
- Добавлены loading, empty, not configured и error states; изменяющие controls отсутствуют.
- Пункт 5 не завершён: связь внутренних ресурсов с Proxmox ID и PostgreSQL reconciliation ещё не реализованы.
- Unit/API-тесты, Go vet/build, frontend tests/lint/build/audit проходят. Browser-сценарий использует mock API и не считается проверкой реального PVE.
- Фактическая синхронизация не проверена: автоматические проверки не имеют секрета API token. Критерий завершения этапа остаётся открытым.

### Тесты

- недоступный Proxmox;
- неверный или просроченный token;
- самоподписанный и доверенный сертификат;
- повторная синхронизация без дубликатов;
- ресурс удалён вне платформы;
- ресурс создан вне платформы.

### Критерий завершения

Панель корректно показывает фактическое состояние тестового Proxmox и не выполняет изменяющих операций.

## Этап 4. Очередь, задачи, логи и аудит

### Задачи

1. Реализовать PostgreSQL-backed очередь.
2. Добавить статусы задач и шагов.
3. Реализовать leases и обнаружение зависших задач.
4. Добавить блокировки на уровне ресурса.
5. Добавить идемпотентность изменяющих запросов.
6. Реализовать потоковое сохранение и отображение логов.
7. Добавить WebSocket-подписку на задачу.
8. Реализовать ограничение и ротацию логов.
9. Добавить скачивание логов.
10. Реализовать аудит критических действий.
11. Определить поведение отмены без ложного обещания rollback.

### Тесты

- перезапуск Management API во время задачи;
- потеря связи с runner;

- маскирование секретов;
- переполнение логов;
- неизвестный результат операции.

### Критерий завершения

Задачи переживают перезапуск панели, не дублируются и предоставляют достаточную информацию для диагностики.

## Этап 5. Runner и безопасный OpenTofu

### Задачи

1. Реализовать аутентифицированный канал Management ↔ Runner.
2. Настроить mTLS или эквивалентную проверку обеих сторон.
3. Реализовать получение задачи runner-ом без открытия внешнего административного API.
4. Реализовать безопасную передачу artifact bundle.
5. Добавить проверки архивов, путей, symlink и размеров.
6. Настроить отдельные рабочие каталоги для задач.
7. Добавить лимиты CPU, RAM, диска, процессов и времени.
8. Реализовать provider allowlist и фиксацию версий.
9. Реализовать:
   - `init`;
   - `validate`;
   - `plan`;
   - сохранение и отображение plan;
   - `apply` после подтверждения.
10. Настроить отдельный state для каждого deployment.
11. Добавить state locking, защищённое хранение и маскирование секретов.
12. Реализовать очистку временных данных после завершения.

### Тесты безопасности

- path traversal;
- symlink за пределы рабочего каталога;
- слишком большой архив;
- запрещённый provider;
- попытка чтения файлов Management VM;
- попытка использования Docker Socket;
- истечение таймаута;
- повторный apply после истечения подтверждения;
- подмена конфигурации между plan и apply.

### Критерий завершения

План и применение тестовой конфигурации выполняются только в Runner VM; apply невозможен для изменённой после подтверждения конфигурации.

## 4. Единый Definition of Done

Этап считается завершённым только если:

1. Функция реализована и доступна через заявленный интерфейс/API.
2. Ошибки обрабатываются и понятны пользователю.
3. Добавлены автоматические тесты для основной логики.
4. Критические сценарии проверены на тестовом Proxmox.
5. Логи не содержат секретов.
6. Изменения БД имеют миграции.
7. Документация обновлена.
8. Не появились новые блокирующие ошибки в уже завершённых этапах.

## 5. Отчётность во время реализации

После каждого этапа предоставляется:

- перечень выполненных задач;
- что фактически проверено;
- результаты тестов;
- найденные ограничения;
- отклонения от плана;
- следующий этап.

Нельзя считать этап выполненным только на основании успешной компиляции.

## 6. Первая операция после утверждения

После явного утверждения начинается **Этап 0**. Реализация функций до проверки совместимости Proxmox, templates и изолированного runner не начинается.
